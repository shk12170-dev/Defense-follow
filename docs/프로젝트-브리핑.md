# 프로젝트 브리핑 (면접·포트폴리오용)

Defense-follow: 쿠팡·롯데카드 개인정보 유출 사고 모의 구현. 근거 자료는 [사고분석-대응보고서.pdf](사고분석-대응보고서.pdf)(9쪽), [presentation.pptx](presentation.pptx)(15장), [README](../README.md)에 있다.

핵심 태도: **무엇을 만들었는지보다 왜 그렇게 설계했고, 한계를 어떻게 알아냈는지**를 말한다. 모든 수치는 합성 로그·단일 PC 기준이라고 함께 밝힌다.

## 1. 30초 소개
> 쿠팡(내부 접근통제 미흡)과 롯데카드(탐지 지연) 사고를 로컬에서 모의 구현했습니다. 내부자의 대량 조회·반출을 탐지하고 자동 대응하는 시스템을 만들고, 방어 효과와 오탐을 측정했습니다. 탐지만으로는 부족하다는 것을 측정으로 확인해서, 서버 하드 쿼터 같은 구조적 한도로 보완했습니다.

## 2. 3분 스토리
1. **문제:** 두 사고 모두 정상 계정으로 데이터를 빼냈다. 쿠팡은 퇴사자·권한 통제, 롯데카드는 이상 징후의 늦은 발견이 문제였다(공개된 보도·조사 내용 기준).
2. **1차 구현:** YAML 규칙 기반 탐지 엔진, 해시 체인 감사 로그, 자동 잠금, 반출 사전 차단.
3. **측정으로 한계 발견:** 저속 공격은 놓치고, 경보가 나기 전에 이미 유출되며, 정상 사용자가 오탐으로 잠겼다.
4. **보완:** 하드 쿼터(반환 전 상한), 허니토큰, 단계적 재인증(TOTP), 주민번호 필드 암호화, 쿼터 강화 4종.
5. **확장:** 시나리오 7개(대량 조회, 새벽 접근, 퇴사자, 반출, 분산 스프레이, 토큰 탈취, 원문 조회 반복)와 규칙 15개. 시나리오마다 한계를 문서에 적었다.
6. **검증:** 자동 테스트 196개, GitHub Actions, 실제 Elasticsearch에서 Sigma 변환 쿼리 실행, Docker 이미지 기동 확인.

## 3. 기억할 숫자 (합성 로그 기준)
| 항목 | 값 |
|---|---|
| 규칙 / 시나리오 / 테스트 / Sigma | 15개 / 7개 / 196개 / 10파일 |
| 대량 조회 유출 | 방어 없음 805건 → **200건**에서 차단 (엄격 프로필 100건) |
| 조회 후 반출 | 5,250건 → 200건 (내보내기는 실행 전에 거부) |
| 분당 10건 저속 공격 8시간 | 4,800건 → 2,000건에서 차단 |
| 정상 요청 응답 | 15.3ms → 16.1ms (약 +5%) |
| 표준 프로필 오탐 | 상담원-일의 5.3% (엄격은 95.3%라 실사용 불가, 그래서 프로필 분리) |
| R14 오탐(가정) | 네트워크 전환이 하루 5%일 때 6.7%, 20%일 때 20.7% |

## 4. 예상 질문과 답변 방향
**Q1. 100% 막을 수 있나요?**
아니요. 하드 쿼터로 유출 상한은 고정했지만 한도 안에서 천천히 빼가는 것은 못 막고, 재인증 코드(TOTP)를 가진 내부자는 재인증을 통과합니다. 그래서 한도·탐지·감사를 겹쳐 썼고, 남은 한계는 보고서에 적었습니다.

**Q2. 왜 머신러닝이 아니라 규칙 기반인가요?**
대응(잠금·재인증)의 근거를 설명할 수 있어야 하고, 데이터가 합성이라 학습 모델은 검증할 수 없습니다. R8은 사용자별 개인 기준선(UEBA)으로 그 방향을 일부 반영했습니다.

**Q3. 오탐은 어떻게 다뤘나요?**
처음에는 R1이 정상 업무를 잠갔습니다. 먼저 재인증을 요구하고 반복할 때만 잠그는 단계적 대응으로 잠금 오탐을 0건으로 줄였습니다(합성 로그 기준). 대신 재인증 마찰이 남습니다. R14·R15는 실제 로그가 없어 가정으로만 측정했다고 밝힙니다.

**Q4. 가장 어려웠던 점은?**
R14 대응입니다. 계정 단위 재인증은 토큰을 훔친 공격자와 정상 사용자를 함께 막았습니다. 로그인 토큰에 발급 IP를 넣고 재인증을 그 밖의 IP에만 적용해, 정상 사용자는 계속 일하게 했습니다.

**Q5. 측정 방법은 믿을 만한가요?**
합성 30일 업무 로그(상담원 5명·관리자 1명)를 같은 엔진·쿼터 함수에 재생해 측정했고 스크립트(`scripts/benchmark.py`, `quota_study.py`, `r14_study.py`)가 저장소에 있어 재현됩니다. 다만 실제 업무 패턴·네트워크 지연은 반영하지 못했습니다.

**Q6. 쿼터를 왜 서버에 두었나요?**
탐지는 이벤트가 난 뒤 반응하므로 경보 전 유출을 못 막습니다. 반환 전에 서버가 직접 거부하면 유출 상한이 고정됩니다. 단, 한도를 낮추면 정상 업무가 막혀서(엄격 프로필 오탐 95.3%) 두 프로필로 나누고 판단 근거를 남겼습니다.

**Q7. 허니토큰은 무엇인가요?**
정상 업무에서는 절대 건드릴 일이 없는 미끼 고객입니다. 접근하면 정상 사용자일 가능성이 낮으므로 R10이 즉시 잠급니다.

**Q8. 토큰 탈취는 어떻게 잡나요?**
R14: 한 계정의 조회가 10분 안에 서로 다른 IP 2개 이상에서 일어나면 잠그지 않고 재인증을 요구합니다. 토큰만 가진 공격자는 인증 코드가 없어 막힙니다. 첫 요청은 샌다는 한계를 같이 말합니다.

**Q9. 관리자 권한 남용은요?**
마스킹 해제는 사유만 적으면 열려서 사유로는 못 막습니다. R15가 60분에 10건 이상의 원문 조회를 감지해 재인증을 요구하고, 하루 20건 하드 쿼터가 상한입니다.

**Q10. 감사 로그는 어떻게 보호하나요?**
각 기록에 이전 해시를 연결하는 해시 체인이라 중간 수정이 검증 스크립트(`verify_audit.py`)에서 드러납니다.

**Q11. SIEM 연동은요?**
Filebeat → Elasticsearch → Kibana를 Docker Compose로 실제 기동했고, Sigma 규칙 10개를 만들어 pySigma로 변환했습니다. 단일 이벤트 규칙은 변환 쿼리를 실제 Elasticsearch에서 실행해 엔진 결과와 대조했습니다. 상관 규칙(여러 이벤트)의 실행 대조는 못 했습니다.

**Q12. 보안 점검은 했나요?**
스스로 점검해 로그인 스로틀(R12), TOTP 재사용 방지, 분산 스프레이 탐지(R13)를 보강했습니다. 의존성은 pip-audit로 점검해 취약 버전을 올렸고 주 1회 점검 워크플로를 넣었습니다.

**Q13. 개발은 어떻게 진행했나요?**
(AI 도구 활용 여부를 묻는 경우) AI 코딩 도구와 함께 개발했습니다. 규칙·임계값의 근거를 측정으로 확인하고 테스트·CI·문서로 검증하는 과정을 제가 판단하고 점검했다는 점을 설명하세요. 사실대로 말하는 것이 안전합니다.

**Q14. 실제 환경에 적용하려면?**
실제 업무 로그로 임계값을 다시 정하고, 프록시 IP만 `X-Forwarded-For`를 신뢰하게 설정하며, 쿼터를 부서·역할별로 세분화하고, 정식 SIEM·SOAR와 연동해야 합니다.

**Q15. 앞으로 더 하고 싶은 것은?**
VMware·pfSense 등으로 실제 네트워크 구간을 나눠 R13·R14를 실제 IP로 검증하고, 잠금 전 관리자 확인 단계와 상관 규칙의 실제 SIEM 실행 대조를 해 보고 싶습니다.

## 5. 하지 말아야 할 표현
- "완벽하게 막는다", "100% 차단"
- 합성 로그 측정값을 실제 운영 수치처럼 말하기 (항상 "합성 로그 기준")
- 쿠팡·롯데카드 사고의 내부 원인을 단정하기 (공개된 보도·조사 내용 기준으로만)
- 실제 데이터를 썼다는 오해: 모든 데이터는 무작위 더미이고 로컬 실행 전용
