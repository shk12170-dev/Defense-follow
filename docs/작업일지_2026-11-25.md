## 5. 발생한 문제와 해결
| 구분 | 문제 | 해결 |
|---|---|---|
| **보안 취약점** | 검색어 `%%`를 넣으면 와일드카드가 제거돼 빈 검색어가 되고, 전체 고객이 조회됨 | 제거 후에도 2글자 이상이어야 하도록 수정, 거부 기록 남김, 회귀 테스트 추가 |
| 측정 버그 | 시나리오 3의 경보 시간이 `-16ms`로 나옴 (앞 시나리오의 경보를 잡음) | 계정·시점별로 필터링, 음수 방지 테스트 추가 |
| 설계 판단 | 정상 업무에서 R5 경고가 31건(상담원·일의 21%)으로 너무 잦음 | 임계값별 측정 후 1,000 → **1,200건**으로 상향 (경고 7건, 유출은 동일) |
| 보안 점검 | 대시보드에 공격자가 입력한 로그인 아이디가 그대로 표시될 위험 | 모든 값 이스케이프, 스크립트가 든 아이디로 실제 확인 |
| 도구 제한 | 로그인 토큰을 읽는 시도가 보안 도구에 의해 차단됨 | 우회하지 않고, 페이지 안에서만 처리하는 임시 화면 → 이후 정식 로그인 대시보드로 대체 |
| Docker | Filebeat 8.x의 데이터 스트림 방식이 인덱스 이름과 충돌해 이벤트가 버려짐 | `setup.dsl.enabled: false` 추가 |
| Docker | 감사 로그 `hash` 필드가 기본 템플릿(ECS)에서 객체 필드라 감사 로그가 0건 | `chain_hash`, `chain_prev`로 이름 변경 |
| Docker | Kibana 5601 포트를 **다른 프로젝트(Wazuh)** 가 사용 중 | 남의 컨테이너를 멈추지 않고 `KIBANA_PORT` 환경변수 도입 |
| 문서 오류 | 시뮬레이터가 "계정은 잠기지 않음"이라고 잘못 출력 (실제로는 R1이 잠금) | Chrome 화면에서 확인 후 문구 수정 |
| 문서 오류 | R5 Sigma의 "오탐 약 5%"는 엔진 측정값인데 Sigma 규칙의 값처럼 보임 | 엔진 값임을 명시하고 Sigma 근사 규칙은 측정하지 않았다고 정정 |
| 테스트 오류 | 시간 계산 오류, 시드 데이터 부족, 15분에 750건을 몰아넣어 R1이 걸린 테스트 | 테스트 데이터 설계 수정 (엔진 버그 아님) |
| 환경 | 셸의 긴 here-document 작성 실패 | 파일 작성 도구로 전환 |

## 6. 배운 점 (정리)
- 접근통제와 마스킹만으로는 "정상 권한으로 천천히 빼가는" 내부자를 막지 못하고, 사후 탐지만으로는 첫 피해를 막지 못한다. **두 계층 + 사전 차단**이 필요하다.
- 임계값은 감으로 정하지 않고 **오탐과 유출 규모를 측정해서** 정해야 한다 (R5 사례).
- 실제로 기동해 봐야 드러나는 문제가 있다 (Filebeat 설정 2건, 포트 충돌은 단위 테스트로는 못 잡았다).
- 측정에서 나온 불리한 결과(오탐, 저속 공격 미탐)를 숨기지 않고 남긴 것이 보고서의 신뢰도를 높인다.
